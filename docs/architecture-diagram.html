Shulchan architecture

The table is one service. Each game engine is its own service, a separate pod in production. Phones talk only to the table. The table calls the engine pod for that game. Video goes through LiveKit.

Table pod
HTTP routes

The door for one-shot calls: create a table, sit down, get a LiveKit token. The phone asks, gets JSON, and the connection ends.

/table socket

The door that stays open. Phones send bets here and receive a new snapshot whenever the hand changes.

Table

The room behind both doors. Seats, secrets, admin, phase. It checks the secret, calls the game pod, then saves Redis and publishes. It does not know the deck or the board.

Game pods
Poker pod

Its own service. Holds the deck and the hand in memory. apply, view, save, load.

Backgammon pod

Its own service. Holds the board and the dice in memory. Same four calls. The table does not care which pod it is.

LiveKit server

A separate service. It accepts the token, then carries every seat's camera. Your game code never sees the video.

Shared
Redis — saved state

One record per table, written by the table pod: seats and secrets, plus the private blob returned by the game pod.

Redis — pub/sub

The table pod publishes "table changed" after each save. Other table pods push a snapshot to the phones they still hold. Pub/sub does not store the hand.

Sitting down with video

  1. 1Player joins the table over HTTP
    2. →
  2. 2Server checks the secret and signs a LiveKit token for room = table id
    3. →
  3. 3Phone connects to LiveKit with that token and publishes the camera
    4. →
  4. 4Other phones in the same room receive that video from LiveKit

One poker action

  1. 1Player taps Raise
    2. →
  2. 2/table checks the secret
    3. →
  3. 3Table pod calls the poker pod, which applies the bet
    4. →
  4. 4Write the table record to Redis
    5. →
  5. 5Publish "table changed"
    6. →
  6. 6Each Node process sends its phones a snapshot

Video and the hand never share a channel. A camera failure does not block a bet, and a bet does not go through LiveKit.

When a Node process dies

  1. 1A table pod or a poker pod dies. Phones reconnect to another table pod.
    2. →
  2. 2That table pod loads the Redis record and calls load on a new poker pod with the private blob.
    3. →
  3. 3The hand continues. In-flight pub/sub messages are gone. The saved record is not.

The poker pod keeps the deck in its own memory. The table pod never reads that blob. It only stores it and hands it back on load. A backgammon pod uses the same load with a board blob instead of a deck blob.
