Shulchan event bus

One in-process bus on the table server. Every table mutation, socket failure, and finished hand or match is published as a named event. A session ledger folds those events into a summary when the table ends or expires.

Where it sits

Socket.IO stays the live channel to phones. The bus is a second, append-only record of what already happened. Publishers call bus.publish after a successful write, or in the existing catch that today only does socket.emit("error"). Subscribers never write table state.

Envelope

Every event uses the same shape. name is the catalog key. tableId is the join code. Secrets, passwords, and LiveKit tokens never appear in data.

{
  "id": "01J…",
  "name": "poker.hand.ended",
  "at": "2026-10-23T10:04:11.221Z",
  "tableId": "K7M2PQ",
  "kind": "poker",
  "actorId": "seat-player-id",
  "data": { "hand": 14, "pot": 840, "winners": [{ "seat": 2, "amount": 840 }] }
}

Module

table/src/events/bus.tsTiny typed pub/sub. publish is sync and never throws into the game path. A subscriber exception is itself published as error.subscriber once, then dropped.
table/src/events/names.tsConst catalog below. Call sites import names so a typo fails the build.
table/src/events/ledger.tsIn-memory map keyed by table id. Updated on each event. Flushed as session.summary on close or expiry, then deleted.

Rules

  • Publish after the table write succeeds, from the same change() wrapper in sockets.ts and the route handlers in routes.ts.
  • One event per fact. A raise is poker.action. If that raise also closes the street, a second event poker.street follows. Hand end is poker.hand.ended.
  • The client does not emit bus events. The server is the source of truth, including backgammon, where the client owns the rules and the server stores the board.
  • The ledger is derived. It is not stored on TableRecord and it is not broadcast on the state socket.

Session summary

Emitted once as session.summary when the last player leaves, the host closes the table, or the TTL sweep removes it. Peak players is the high-water mark of seated players, not the count at the end.

{
  "name": "session.summary",
  "tableId": "K7M2PQ",
  "kind": "poker",
  "data": {
    "durationMs": 4980000,
    "peakPlayers": 6,
    "joins": 8,
    "leaves": 7,
    "hands": 42,
    "streets": { "flop": 31, "turn": 18, "river": 9 },
    "showdowns": 9,
    "rebuys": 3,
    "chipsRebought": 1500,
    "errors": 4,
    "endReason": "expired"
  }
}

Backgammon uses the same event. hands is omitted. matches is the count of backgammon.match.ended, and points is the sum of cube scores. rounds on a backgammon summary is the number of completed turns (a roll plus the moves that followed), which is what “amount of rounds” means for that game. For poker, rounds are betting streets inside hands, counted on poker.street.

What the ledger counts

peakPlayersMax of playerCount on table.joined.
roundsPoker: count of poker.street. Backgammon: count of backgammon.turn.
hands / matchesCount of the matching *.ended event.
errorsCount of error.* for this table, with the last five messages kept for the summary.
rebuysCount and chip sum from poker.rebuy.
endReasonclosed from table.closed, or expired from table.expired.

Out of the first cut

  • No client SDK and no replay socket. Summaries are server logs until a host screen asks for them.
  • No per-card hole cards and no dice faces. Those are game secrets or noise. The summary keeps counts and winners.
  • Redis streams can replace the in-memory ledger later without renaming events. The bus interface stays publish / subscribe.
