Monitoring and analysis

What Shulchan should record so we can see whether people open tables, sit down, play a hand or a game, stay on video, and where the service fails.

Client (Expo) · table service · poker engine · backgammon engine · LiveKit · Redis · Google host sign-in. No passwords, player secrets, admin secrets, host tokens, or LiveKit tokens in any event or log.

Questions this system answers

  • How many hosts sign in, open a poker table, or open a backgammon table, and how many guests join with a code and password.
  • Where join fails: wrong password, full table, join limit, missing table, bad name.
  • Whether a seated table actually starts a hand or a backgammon game, and how long a session lasts.
  • Who leaves, who is removed, and whether admin is transferred before the host disappears.
  • Whether video connects, drops, or is unavailable (503) on a given table.
  • Socket rejects, action errors, engine errors, and Redis misses, tied to a table id and a request, without card or dice values that identify a private game.

Rules

Product events are for funnels and retention. Service logs are for failures and latency. The same name can appear in both when a user action and a server outcome both matter (join refused, video unavailable).
  • Every record has ts, service (client, table, poker, backgammon), and env (local or prod).
  • Table-scoped records include tableId (the 6-character code) and kind (poker or backgammon).
  • Player-scoped records include playerId and seat. Never secret, password, adminSecret, bearer tokens, or LiveKit JWTs.
  • Host records use a stable hostId derived from the Google account, plus a boolean signedIn. Email stays in auth storage; it is not copied into analytics.
  • Client events include platform (ios, android, web), appVersion, and a sessionId created when the app process starts.
  • Server logs include requestId on HTTP and socketId on the /table namespace. Duration is ms.
  • Poker logs may include street, action name, and chip amount. They do not include hole cards. Backgammon logs may include a move count and dice totals, not the full board, unless a debug flag is on for one table.
  • Sample success-path state broadcasts. Always keep errors, joins, leaves, and hand or game boundaries.

Metrics to chart

  • Funnel, daily: app_open → host_sign_in_succeeded or join_opened → table_created or player_joined → socket_connected → hand_started or bg_roll.
  • Join refusal rate by reason.
  • Tables created that never start a hand or a game within 10 minutes.
  • Median seatedMs and hands or moves per seat.
  • Socket reject rate, action reject rate, engine error rate, Redis p95.
  • Video: token failure rate, connect rate among seated players, median time with camera on.
  • HTTP status counts for POST /api/games, POST /:id/join, POST /:id/livekit.

First dashboards

  1. Tonight’s tables. Open tables, seated players, last event, video on or off, last error.
  2. Join health. Attempts, successes, wrong password, full, rate limit.
  3. Play. Hands started, actions, rebuys, backgammon games finished, empty-table lifetime.
  4. Failures. error logs from table, poker, and backgammon, grouped by op and reason.
Ship order: table-service HTTP and socket logs first (they already sit on every join and action), then the client funnel events, then engine hand boundaries, then video and ads. Alerts start with engine error rate, join 5xx, and LiveKit 503, not with product counts.
